What are we building? (5W + 1H)

QuestionAnswer
WhatA paper-trading (virtual money) stock application: accounts start with $100,000 of virtual cash, place BUY/SELL trades, and see their portfolio, cash, and history — through a web page and an API.
WhyIt adds the two skills the Loan project didn't cover: a frontend (a real web page calling your API with JavaScript) and multi-table business logic (a trade must check cash, record itself, and update the balance — all in one transaction).
WhoThree kinds of clients use the same API: the browser page (frontend/), the Swagger UI at /docs, and the demo.py script. That is the core lesson — one backend, many clients.
WhenEverything runs while uvicorn is running. Trades execute instantly at the price you type (no live market feed — that keeps the learning focused).
WhereOn your machine at http://127.0.0.1:8000 (page) and /docs (API), data in trades.db; the source code also lives in your GitHub repository via git push.
HowBrowser JavaScript fetch() → FastAPI route → Pydantic validation → business rules (cash/shares checks) → SQLAlchemy ORM → SQLite. The same FastAPI process also serves the HTML/CSS/JS files.

Libraries used

  • FastAPI — the web framework: decorated Python functions become HTTP endpoints, with automatic docs at /docs. New in this project: StaticFiles, which lets the same app serve the frontend files.
  • Uvicorn — the ASGI server listening on port 8000 and passing every request (page loads and API calls) to FastAPI. --reload restarts it when you save.
  • SQLAlchemy — the ORM: Python classes for tables, Python method calls instead of raw SQL, and sessions that make "check cash + save trade + update balance" one atomic commit.
  • Pydantic — validation of incoming JSON (types, required fields) and shaping of outgoing JSON, including the computed total_value field.
  • SQLite (built into Python) — the zero-setup file database behind it all.
  • Browser Fetch API (built into every browser, used in script.js) — JavaScript's way of making HTTP calls; the frontend equivalent of urllib.
  • urllib.request & json (standard library, demo.py) — HTTP + JSON without installing anything.
  • Git (tool, not a library) — version control: add → commit → push snapshots your source code to GitHub.
Compared to the Loan project: same skeleton (database.py / models.py / schema.py / main.py), three new ideas — a frontend served by the API, money-moving business rules that touch two tables, and Git/GitHub for versioning. Everything you learned there transfers directly.

Architecture diagram

Same layered idea as the Loan project, with one addition: the FastAPI process now serves the frontend files too, so the browser talks to it twice — once to load the page, then repeatedly for data.

Why one process for both frontend and API?

Big companies often run the frontend and backend as separate deployments. For learning, serving both from FastAPI removes two whole problems: no second server to start, and no CORS (cross-origin) configuration — because the page and the API share the same address, the browser considers them the same site.

The mount order matters: /api/* routes and /docs are registered first, and StaticFiles is mounted at / last, so it only catches whatever the API didn't claim.

Interesting design point: there is no "holdings" table. Your current position in a stock is calculated from the trade history (BUYs minus SELLs) by the portfolio endpoint. Storing only facts (trades) and computing state (holdings) avoids the two ever disagreeing — a pattern worth remembering.

LineExplanation
1–12Identical to the Loan project except the filename on line 4 (trades.db). engine = the app-wide door to the database; SessionLocal = factory producing one short-lived session per request; Base = the registry models attach to; autocommit=False = nothing saves until db.commit().
14–19get_db() opens a session, yields it to the endpoint, and the finally guarantees it closes even if the endpoint raised an error. One extra reason this matters here: a trade modifies two tables (trades + the account's cash). Because both changes happen in the same session and one commit(), they succeed or fail together — you can never end up with cash deducted but no trade recorded.

1–4Same imports as before; the leading dot in .database means "from this same package".

30The reverse direction: trade.account walks from any trade back to its owner.

LineExplanation
5–7Creating an account needs only a name and email — deliberately not cash_balance, so the $100,000 default in models.py can't be overridden by a client.
9–14The shape of an incoming trade order. Pydantic guarantees the types: send "quantity": "ten" and FastAPI answers 422 before your code runs. Whether it's a legal trade (enough cash, valid side) is business logic and lives in main.py — types vs rules is a separation worth noticing.
16–31The outgoing trade. from_attributes=True lets Pydantic read straight off SQLAlchemy objects. Lines 28–31: total_value is computed at response time (quantity × price) — never stored, so it can never disagree with the stored fields.
33–41Account response includes the full nested trade list via the ORM relationship — one GET returns the account and everything it ever did.
43–47Holding is a pure output shape with no matching table — proof that schemas and tables are independent ideas. Holdings exist only as math over trades.
49–54The portfolio bundle: cash + the holdings list + two totals. main.py fills this in; the schema just guarantees its shape (and documents it automatically in /docs).

  141. average_buy_price=round(avg, 2),
  142. invested_amount=round(net * avg, 2)))

  146. cash_balance=round(account.cash_balance, 2),

LineExplanation
1–11Familiar setup plus one newcomer: StaticFiles (line 3) — FastAPI's built-in file server for the frontend. Line 9 creates both tables on startup; line 11 is the app object Uvicorn serves.
15–19First helper. Three endpoints need "fetch account or 404", so it's written once. When you see yourself copy-pasting the same 4 lines, that's the signal to extract a helper.
21–29Second helper: how many shares of one symbol does an account really hold? Fetch its EXECUTED trades for that symbol (22–25), then add BUY quantities and subtract SELL quantities (26–28). There is no "shares" column anywhere — position is always derived from trade history.
33–42Create account: duplicate-email guard (35–37) then the familiar add → commit → refresh trio (39–41). The $100,000 comes from the model default — this function never mentions it.
44–56List, get-one (via the helper, so it's a one-liner on line 50), and delete. Delete cascades to the account's trades thanks to models.py.
60–69The heart of the app begins. Fetch the account (62), normalize input so "aapl"/"buy" work (63–64), then two rule gates: valid side (65–66) and positive numbers (67–69).
70–78The money movement. Line 70 computes the cash impact once. BUY branch (71–74): reject if it costs more than the cash on hand, otherwise subtract. SELL branch (75–78): reject if the account doesn't hold enough shares (using net_shares), otherwise add the proceeds. Notice the account object is modified in plain Python — SQLAlchemy tracks the change automatically.
79–84Record the trade and commit. This is the key moment: the cash change (74 or 78) and the new trade row (81) are saved by the same commit on line 82 — one atomic unit. If anything failed before this line, neither change was saved.
86–96Trade listing with three optional query-string filters, chained onto the query only when provided — e.g. /api/trades?account_id=1&side=BUY. The frontend uses the account_id filter for the history table.
98–114Cancel = the reverse of placing. Guard against double-cancel (103–104, otherwise cash would be refunded twice!), reverse the cash effect (106–110: cancelled BUY refunds money, cancelled SELL takes the proceeds back), and flip status instead of deleting (111) — the row remains as history.
118–132Portfolio, phase 1 — gather: walk the account's executed trades and bucket them per symbol (setdefault creates a bucket on first sight of a symbol), accumulating bought quantity, bought cost, and sold quantity.
133–143Phase 2 — compute: net position (135), skip fully-sold symbols (136–137), average buy price = total cost ÷ total bought (138), then build Holding objects and sum the invested amounts.
144–149Phase 3 — assemble the PortfolioResponse: cash + holdings + totals, with total_value = cash plus invested. Pure calculation, no writes — GET endpoints should never change data.
151–152The frontend mount, deliberately last: routes are matched in order, so /api/* and /docs are claimed first and StaticFiles catches the rest. html=True makes "/" serve index.html. Put this line first and it would swallow every request — a classic beginner trap.
Pattern upgrade from the Loan project: Loan endpoints wrote to one table. place_trade and cancel_trade write to two (trades + accounts) under a single commit — your first real transaction. That idea scales all the way up to real banking systems.

4–14The JavaScript twin of demo.py's call() helper. fetch() sends the HTTP request; await pauses until the reply arrives without freezing the page. 16–22The banner: set the text, switch the CSS class (green/red), and auto-hide after 4 seconds. All the styling lives in style.css; JS only flips class names.
24–26Reads which account is selected in the dropdown, converted from string to number.
28–40Fill the dropdown: GET the accounts, clear old options (32), create one <option> per account (33–38) where value holds the id the API needs and the visible text holds the name, then trigger the first refresh.
42–53Refresh, part 1 — portfolio: one GET fills the two money cards (47–48), then .map() turns each holding into a <tr> string, joined and injected into the table body (49–52). Line 53: if there are no holdings the || falls back to a friendly empty-state row.
55–65Refresh, part 2 — history: fetch this account's trades using the query filter, newest first (slice().reverse() copies before reversing). 67–73Cancel: call the endpoint, announce it, refresh. The try/catch around every action is the frontend's version of Python's try/except — errors become banners instead of a broken page.

Running & deploying the app — three environments

These steps match your actual generated code: endpoints in app/routes/trades.py plugged into app/main.py via a router, tables created by init_db(), and the database path resolved in app/database.py. The run command is the same everywhere; only the surroundings change.

Two flags you will meet in the cloud steps — worth understanding once:

--host 0.0.0.0 — locally, Uvicorn listens on 127.0.0.1, which means "this machine only". On a cloud server, requests arrive from outside the machine, so the server must listen on all network interfaces: that is what 0.0.0.0 means.

--port $PORT — cloud platforms decide which port your app gets and publish it in an environment variable named PORT. $PORT reads that variable, so your start command works no matter which port the platform assigns.

The one warning that applies to both platforms

Your SQLite data is temporary in the cloud. Both Render and Railway give your app an ephemeral filesystem: every redeploy (and, on Render's free tier, every spin-down) starts from a fresh copy of your repository — and since .gitignore correctly keeps trades.db out of Git, the database starts empty each time. For a learning demo that's fine, and it's a feature in disguise: you get a clean slate on every deploy.

The real-world fix, when you're ready for it, is a managed database: both platforms offer hosted PostgreSQL, and because of how database.py is structured, switching means reading the connection string from an environment variable instead of building a SQLite path — one focused change in one file. That's a great next project, and a direct payoff of the layered architecture in this guide.
